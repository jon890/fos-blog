# ADR-035: 카테고리 URL을 소문자로 정규화하고 canonical을 그 형태로 고정한다

- **결정**: 카테고리 경로를 소문자로 정규화한 URL을 대표 형태로 삼는다.
  `sitemap.xml`은 정규화된 URL만 내보내고 같은 URL을 두 번 싣지 않는다.
  카테고리 페이지의 canonical은 요청 경로가 아니라 정규화된 형태를 가리킨다.
  정규화 함수는 `src/lib/path-utils.ts`에 두고 sitemap과 페이지가 같은 함수를 쓴다.
  대표 URL에서도 원본 표기의 글을 빠짐없이 조회하도록 폴더 경로 접두사는 대소문자를 구분하지 않고 비교한다.
- **맥락**: `sitemap.xml`의 `/category` URL 72개 중 고유한 것은 52개뿐이었다.
  `sitemap.ts`가 `categoryPages`와 `folderPages`를 각각 만들어 이어 붙이는데,
  전자는 `categories` 테이블의 `slug`를, 후자는 글 경로에서 계산한 폴더 경로를 쓴다.
  최상위 카테고리는 두 값이 항상 같아 20건이 그대로 중복됐다.
  여기에 더해 `AI`와 `ai`처럼 대소문자만 다른 URL 2쌍이 함께 실렸다.
- **왜 canonical만으로는 부족했는가**: canonical 자체는 이미 있었으나 요청 경로를 그대로 반사했다.
  `/category/AI`는 자신을, `/category/ai`도 자신을 대표로 선언해 중복을 하나로 모으는 기능이 없었다.
  폴더 레코드 조회는 MySQL의 기본 collation 때문에 대소문자를 구분하지 않지만,
  글 경로 접두사를 거르는 JavaScript 비교는 원래 대소문자를 구분했다.
  sitemap과 canonical만 고치면 외부 링크나 크롤러의 추측으로 다른 조합이 다시 색인될 수 있고,
  대표 URL에서 일부 글이 누락될 수도 있으므로 조회 비교도 함께 맞춘다.
- **대안 기각**:
  - **대문자를 포함한 저장소 원본 표기를 유지** 기각 — 글 경로와 표기는 맞지만 URL 관례에서 벗어나고,
    대소문자를 구분하지 않는 조회 특성상 어느 쪽을 골라도 반대 표기가 계속 유입된다.
    어느 하나로 고정하는 것이 목적이므로 관례를 따른다.
  - **대소문자가 다른 URL을 301로 리디렉션** 기각 — 라우트가 대소문자를 구분하지 않아
    정규 형태를 판별하려면 요청마다 비교와 분기가 필요하다.
    canonical로 같은 효과를 얻으면서 기존 링크는 그대로 동작시키는 편이 비용이 낮다.
  - **sitemap에서 카테고리를 통째로 제외** 기각 — 글이 많은 카테고리는 탐색 가치가 있다.
    얇은 카테고리를 가려내는 것은 별도 판단이라 이 결정에 섞지 않는다.
- **트레이드오프**: 카테고리 URL은 소문자, 글 URL은 저장소 원본 표기를 유지하므로 사이트 안에서 두 표기가 공존한다.
  글 URL까지 소문자로 바꾸면 이미 색인된 300여 개 주소가 한꺼번에 바뀌므로 이번 범위에서 제외한다.
- **적용 범위**: `sitemap.xml`의 카테고리 항목과 `/category/[...path]`의 canonical에 적용한다.
  `/tag/[name]`과 `/series/[name]`도 요청 값을 canonical로 반사하지만 현재 sitemap이 만드는 중복 범위에는 포함되지 않는다.
  외부 유입으로 생길 수 있는 대소문자 중복은 별도 범위이며, 이들을 sitemap에 넣게 되면 같은 결정을 함께 적용한다.
